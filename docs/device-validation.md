# Android 真机验证清单

**状态：尚未执行完整真机验收。** 本文是测试步骤与通过条件，不是测试通过报告。每次运行应记录设备型号、Android/API 版本、安全补丁版本、CPU ABI、WebView 版本、APK SHA-256、签名、versionCode，以及 payload、upstream 和 runtime 锁文件摘要。

## 测试前提

- 使用 ARM64 测试设备，并保留已安装的官方 Termux 及其数据。检查两个应用能同时安装和启动，不以卸载或清除数据换取测试环境。
- 安装前确认本应用包名为 `io.github.mikyan.pipocket`，官方 Termux 包名保持 `com.termux`。
- 为启动、解包、离线 deb 安装、升级备份与旧运行环境预留足够空间；记录实际占用，不预设固定 APK/安装尺寸。
- 使用专门的测试提供商配置和临时工作文件。恢复测试优先使用可控模型与无外部副作用的工具任务。
- 不将 token、API key、授权文件或完整带凭据日志附到测试报告。

## 2. 冷启动与离线组件准备

首次安装后，在没有配置在线提供商的情况下启动。可暂时断开网络，确认本地组件安装不依赖临时 npm/apt 下载；在线模型功能不列入这一项。

检查准备进度、运行状态通知、首次展开耗时、second-stage 和 dpkg 退出码。验证 Node 版本、SQLite 内存表访问、bash 子进程、Git、ripgrep、fd 和 npm 均正常，并检查 dpkg 审计无异常。检查配置完成标记只在所有步骤成功后写入。

随后进入原版前端，确认不显示终端、不要求输入启动命令。再次冷启动应复用同一 payload 和持久数据，不重复完整展开。恢复网络后，分别测试 Node HTTPS、Git HTTPS 与提供商请求，验证证书链工作正常，不能通过关闭证书校验解决问题。

## 4. Durable 任务恢复

创建一个可控的多步骤任务：至少包含已完成步骤、尚未完成步骤和可观察的本地结果。记录会话 ID、run ID、完成步骤序号及工具输出，然后执行下列生命周期测试。不要重新发送原始用户请求。

| 中断场景 | 恢复动作 | 通过条件 | 状态 |
| --- | --- | --- | --- |
| 切后台、锁屏、回前台 | 点击原应用 | 保持原会话；仍存活时复用服务 | 待验证 |
| Activity 重建 | 回到界面 | 不重复建 run，不重装 runtime | 待验证 |
| 系统回收应用进程 | 手动重新打开 | 同数据恢复未完成 run，已提交步骤不重复 | 待验证 |
| launcher/server 异常退出 | 重试或重新打开 | 原版 supervisor/恢复流程正常；无双实例 | 待验证 |
| 系统设置中强行停止 | 手动重新打开 | 停止期间不承诺继续执行；重开后恢复同数据 | 待验证 |
| 设备重启 | 解锁后手动打开 | 提供商配置、会话和工作文件保留 | 待验证 |
| 流式响应断网 | 恢复网络并观察 | 无重复用户消息；错误与恢复状态清楚 | 待验证 |
| 可安全重放工具中断 | 重开应用 | 遵循上游恢复策略，结果一致 | 待验证 |
| 不可安全重放工具中断 | 重开应用 | 明确 interrupted/需处理，不盲目重复副作用 | 待验证 |

用户停止前台服务与低内存回收是不同机制，要分别记录。可通过测试设备的 Android 设置操作；如使用 adb，只执行 `am force-stop io.github.mikyan.pipocket`，不对用户现有 Termux 执行停止或数据清理。

核心判定是原 run 的状态推进与工具结果。聊天历史存在、前端能重新打开或一条新 run 完成，都不足以证明持久任务恢复通过。

## 5. 安装与配置中断

分别在 payload 解包、符号链接建立、second-stage、dpkg 配置和目录切换期间停止应用，然后手动重开。确认用户 HOME 不被删除，未完成配置不被视为成功，日志能区分失败阶段。已有 second-stage 锁不应让测试误判配置完成。

检查离线包已安装状态和 `dpkg --audit` 输出，排查半配置包。若某种中断无法自动恢复，将它记录为缺陷，不用“清除数据后可以启动”替代恢复验收。

## 6. 升级、备份与回退

先用版本 A 建立测试会话、提供商配置与 `workspace` 哨兵文件，记录校验和。准备同签名、更高 versionCode 的版本 B，并明确其上游与运行环境锁变化。

1. 在 A 的服务仍工作时安装 B 并打开。确认不会在任务运行时替换正在使用的环境；如果复用旧服务，界面给出组件升级需完整停止的提示。
2. 完整停止本测试应用后重新打开，验证旧进程锁已释放。
3. 确认 `files/backups/<时间戳>/` 中包含 `.pi-pocket` 和 `.pi/agent` 的升级前副本，以及 `backup.json`。
4. 确认 `usr.previous-<时间戳>` 被保留，新 payload 在 `usr` 配置完成，数据库只由一个实例打开。
5. 检查原会话 ID、run ID、提供商配置、上传文件与工作文件。`workspace` 应保持原内容；它不属于自动备份范围。
6. 在目录切换中断后重开，确认切换日志能够恢复可用目录或明确报告问题，不能悄悄创建空白 HOME。
7. 人为使 B 启动失败，确认不会自动让 A 读取已经迁移的数据库，也不会自动覆盖用户的新数据。

上游 schema 迁移可能不可逆。需要回退时，应先保存失败现场和当前数据，再确定迁移前备份与旧代码是一组；恢复会舍弃备份之后的数据变更，应由操作者明确选择。保留的旧 `usr` 只是恢复材料，不是数据库回滚保证。

自动备份位于同一应用的私有目录，不防设备丢失、卸载或清除数据。升级验收还应单独确认向设备外导出所需数据的操作可行；本版未承诺完整备份/恢复界面。
